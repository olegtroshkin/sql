## Задание 1. СУБД

### 1.1. Бюджетирование, финансовая отчётность, прогноз рисков

**Тип: реляционная СУБД (OLTP), например PostgreSQL / Postgres Pro, MS SQL Server или Oracle.**

Почему:

- **ACID-транзакции.** Проводка бюджета, перераспределение средств между статьями и сметы должны выполняться полностью или не выполняться совсем. Для финансов это обязательное требование.
- **Строгая схема и ограничения целостности** (PRIMARY KEY, FOREIGN KEY, CHECK, NOT NULL). Проект, этап, статья бюджета, контрагент и платёж жёстко связаны, а СУБД не даст записать «платёж без проекта» или отрицательную сумму там, где она недопустима.
- **SQL с JOIN, агрегатами и оконными функциями** хорошо подходит для финансовых отчётов (план/факт, cash flow, отклонения по этапам).
- **Аналитика и прогнозирование.** По мере роста данных стоит добавить колоночное хранилище (DWH) поверх основной БД, например ClickHouse или Greenplum. Данные туда грузятся через ETL, а модели рисков считаются уже там, чтобы тяжёлая аналитика не мешала транзакционной нагрузке.

#### 1.1.* Хеширование стало медленным: какое API использовать

Зависит от того, что хешируется и зачем.

- **Аппаратное ускорение через криптобиблиотеки.** Можно перенести вычисление хешей из СУБД (например, из медленного `pgcrypto`) в приложение или сервис и использовать **OpenSSL EVP API** или **Intel ISA-L / IPP Crypto**. Они задействуют процессорные инструкции SHA-NI и AVX2/AVX-512, и прирост получается кратный.
- **Массовое хеширование на GPU** через **CUDA** (NVIDIA) или **OpenCL**. Это оправдано, когда хешируются большие объёмы: контроль целостности документов, файлов проектной документации, дедупликация.
- **Если хеш не криптографический** (контрольные суммы, ключи партиционирования, дедупликация), стоит взять быстрые алгоритмы: **xxHash**, **BLAKE3** (многопоточность и SIMD) или CityHash/MurmurHash. Они в разы быстрее SHA-256.
- **Внутри PostgreSQL** можно перейти со старых функций `pgcrypto` на встроенные `sha256()` (начиная с PG 11), включить параллельное выполнение запросов и хранить посчитанный хеш в отдельном столбце, а не вычислять его каждый раз.
- **Если причина в повторных вычислениях**, поможет кэширование результатов в **Redis** (через его API).

### 1.2. Лендинги и CRM

**Лендинги: документо-ориентированная NoSQL (MongoDB) и/или key-value (Redis).**

- У каждого проекта свой лендинг со своим набором полей в формах (квиз, ипотечный калькулятор, выбор планировки). Документной БД не нужна единая жёсткая схема, поэтому новый лендинг запускается без миграций.
- Высокая скорость записи и горизонтальное масштабирование (шардирование) выдерживают пики трафика во время рекламных кампаний.
- Redis подходит для сессий, кэша страниц, счётчиков и очередей отправки лидов в CRM.

**CRM: реляционная СУБД (PostgreSQL) или та же документная (MongoDB).**

- В CRM есть устойчивые сущности и связи: лид, клиент, менеджер, сделка, объект, воронка. Здесь важны JOIN, отчётность по продажам и целостность (один лид не должен потеряться или задвоиться).
- При этом нужна гибкость, чтобы хранить «сырые» данные лида из разных лендингов.

#### 1.2.* Можно ли обойтись одной СУБД

**Да. Оптимальный вариант — PostgreSQL с типом данных JSONB.**

Реализация:

- **Ядро CRM** хранится в обычных реляционных таблицах (`clients`, `deals`, `managers`, `projects`) с внешними ключами.
- **Таблица `leads`** содержит фиксированные поля (`id`, `project_id`, `phone`, `source`, `utm`, `created_at`) и поле `payload JSONB` для произвольных данных конкретного лендинга. По `payload` строится **GIN-индекс**, поэтому поиск по полям внутри JSON остаётся быстрым.
- Лендинги пишут лиды через единый API (например, REST-сервис или PostgREST). Маркетологи и менеджеры видят их в CRM сразу, без интеграций и ETL.
- Уведомления менеджерам о новом лиде можно сделать через `LISTEN/NOTIFY` или триггеры.
- Для масштабирования используются партиционирование `leads` по дате или проекту, реплики на чтение и pgBouncer.

Альтернатива: **только MongoDB** (отдельная коллекция на каждый лендинг, общая коллекция лидов, `$lookup` для связей, Change Streams для уведомлений). Но для отчётности по продажам и связанных сущностей PostgreSQL удобнее, и его же можно переиспользовать из задачи 1.1.

### 1.3. База знаний отдела контроля качества

**Тип: документо-ориентированная СУБД (MongoDB) с моделью дерева. Для поиска можно добавить Elasticsearch / OpenSearch.**

Почему:

- Нормативы, регламенты, выдержки из СП/СНиП и обучающие материалы по своей природе являются документами разной структуры: текст, вложения, видео, тесты, версии.
- Структура «по подразделениям компании» — это иерархия (департамент → отдел → направление → документ). В документной БД она моделируется просто: вложенными документами или полями `parent_id` / `path`.
- Схема понятна даже без глубоких знаний SQL: один документ соответствует одному материалу со всеми его атрибутами.
- Полнотекстовый поиск по регламентам здесь критичен, поэтому полезен поисковый движок Elasticsearch или OpenSearch.

#### 1.3.* Можно ли переиспользовать СУБД из предыдущих задач

**Да, удобнее всего PostgreSQL из 1.1 и 1.2.** Реализация:

- **Отдельная схема** (`knowledge`) с собственными правами доступа, чтобы база знаний была изолирована от финансов и CRM.
- **Расширение `ltree`** для хранения иерархии по структуре компании (`company.construction.qc.concrete`). Оно позволяет быстро выбрать всё поддерево отдела.
- **JSONB** для разнородных атрибутов материалов.
- **Встроенный полнотекстовый поиск** (`tsvector` с русской морфологией, GIN-индекс), так что отдельный Elasticsearch на старте не нужен.
- Файлы (PDF, видео) лучше хранить в объектном хранилище (S3-совместимом, например MinIO), а в БД держать только ссылки и метаданные.

Если в 1.2 выбрали MongoDB, базу знаний так же удобно сделать отдельной базой (database) в том же кластере MongoDB.

### 1.4. Логистика: маршруты и распределение курьеров

**Тип: графовая СУБД, например Neo4j (или Memgraph, ArangoDB).**

Почему:

- Задача по своей сути графовая. Узлы — склады, объекты, офисы, точки сдачи документов, курьеры, машины. Рёбра — дороги или участки маршрута со свойствами: расстояние, время, ограничения по тоннажу.
- Графовые СУБД хранят связи напрямую (index-free adjacency), поэтому обход связей не требует дорогих многоуровневых JOIN и остаётся быстрым даже на глубине 5–10 переходов.
- В них есть готовые алгоритмы (Neo4j Graph Data Science): кратчайший путь (Dijkstra, A*), обходы, кластеризация точек доставки, поиск «узких мест».
- Язык Cypher наглядно описывает маршруты: `MATCH path = shortestPath((s:Warehouse)-[:ROAD*]-(o:Site)) ...`.

Распределение курьеров по маршрутам (задача VRP) обычно решает отдельный оптимизатор, например Google OR-Tools. Он берёт граф и матрицу расстояний из Neo4j и записывает результат обратно. Альтернатива на реляционной базе — PostgreSQL + PostGIS + pgRouting.

#### 1.4.* Подключать ли закупки к СУБД логистов

**Лучше дать закупкам свою СУБД и связать её с логистикой.**

- Закупки — это заявки, тендеры, договоры, счета, поставщики и остатки. Это транзакционные финансовые данные, где важны ACID, строгая схема и связь с бюджетами из 1.1. Поэтому здесь нужна **реляционная СУБД**: отдельная схема в том же PostgreSQL, что и бюджетирование, либо учётная система вроде 1С:ERP.
- Связка с логистами: подтверждённый заказ поставщику (что, сколько, откуда, на какой объект, к какой дате) передаётся в графовую БД как задача на доставку. Передача идёт через CDC/брокер сообщений (Debezium + Kafka, есть Neo4j Kafka Connector) или через API. Статусы доставки возвращаются обратно в закупки.
- В сам граф закупки стоит подключать только для аналитики сети поставщиков: какой поставщик ближе к объекту, альтернативные цепочки поставок, риски зависимости от одного поставщика. Основной учёт закупок в графовой БД держать не нужно.

### 1.5.* Можно ли решить все задачи одной СУБД

**Технически да: PostgreSQL (или российский Postgres Pro) как мультимодельная СУБД.**

| Задача | Чем закрывается в PostgreSQL |
| --- | --- |
| 1.1 Финансы | Реляционная модель, ACID, ограничения целостности, оконные функции |
| 1.2 Лендинги и CRM | JSONB + GIN-индексы, партиционирование, LISTEN/NOTIFY |
| 1.3 База знаний | `ltree`, JSONB, полнотекстовый поиск `tsvector` |
| 1.4 Логистика | PostGIS + pgRouting (маршруты на карте) и/или Apache AGE (графы, openCypher) |
| Аналитика | Расширения Citus / TimescaleDB либо реплика для отчётов |

Альтернатива — нативно мультимодельная **ArangoDB** (документы, граф и key-value в одном движке, язык AQL). Она хорошо закрывает 1.2–1.4, но для финансового учёта из 1.1 уступает классической реляционной СУБД по зрелости транзакций и инструментам отчётности.

**Оговорка.** В реальной крупной компании чаще выбирают подход *polyglot persistence*: PostgreSQL как ядро (финансы, закупки, CRM, база знаний), Neo4j для логистики, Redis для кэша, ClickHouse для аналитики, а всё это связывается через шину данных (Kafka). Одна СУБД проще в поддержке, лицензировании и обучении персонала. Но она становится единой точкой отказа, её сложнее масштабировать, и в «чужих» для неё задачах (глубокие графовые обходы, тяжёлая аналитика) она будет работать медленнее специализированных решений.

Разумный компромисс: начать с PostgreSQL на всё и выносить в специализированные СУБД только те области, где появляются реальные проблемы с производительностью (в первую очередь логистику и аналитику).

## Задание 2. Транзакции

### 2.1. Пополнение баланса телефона: шесть шагов

С точки зрения СУБД пополнение — это одна транзакция, в которой участвуют два счёта: банковская карта (или кошелёк) пользователя и лицевой счёт абонента у оператора. Деньги должны одновременно списаться с одного счёта и зачислиться на другой. Если хотя бы один шаг не выполнен, всё отменяется (принцип ACID).

1. **Начало транзакции (BEGIN).** Пользователь ввёл номер телефона и сумму и подтвердил платёж. Система открывает транзакцию, с этого момента все изменения временные.
2. **Проверка входных данных.** Номер телефона существует и обслуживается оператором, абонентский счёт активен, сумма положительная и укладывается в лимиты (минимальный и максимальный платёж, суточные лимиты по карте).
3. **Проверка и блокировка средств на счёте плательщика.** Система проверяет, что на карте достаточно денег, и блокирует строку счёта (`SELECT ... FOR UPDATE`). Блокировка нужна, чтобы параллельная операция не потратила те же деньги. Если средств не хватает, выполняется ROLLBACK, и пользователь получает отказ.
4. **Списание суммы с карты.** `UPDATE accounts SET balance = balance - сумма WHERE id = карта`.
5. **Зачисление суммы на баланс телефона и запись в журнал.** `UPDATE phone_accounts SET balance = balance + сумма WHERE phone = номер`. Одновременно создаётся запись об операции в журнале платежей: кто, кому, сколько, когда, статус и уникальный идентификатор операции, который защищает от повторного проведения.
6. **Фиксация транзакции (COMMIT) и уведомление.** Все изменения записываются окончательно и сохраняются даже при сбое (durability). Пользователь получает чек или SMS о зачислении. Если на любом из шагов 2–5 произошла ошибка (нет связи с оператором, таймаут, сбой), выполняется **ROLLBACK**: баланс карты и баланс телефона возвращаются в исходное состояние, и пользователь видит сообщение об ошибке.

Как здесь работают свойства ACID:

- **атомарность:** списание без зачисления невозможно;
- **согласованность:** сумма денег в системе не меняется, баланс не уходит в минус;
- **изоляция:** параллельные платежи не видят промежуточного состояния;
- **долговечность:** после COMMIT данные не теряются.

### 2.1.* Пополнение через автоплатёж

Основная транзакция (шаги 3–6) остаётся той же. Разница в том, что её запускает не пользователь, а система, поэтому добавляются шаги до и после неё.

1. **Срабатывание условия.** Автоплатёж запускается по расписанию (например, 1-го числа каждого месяца) или по порогу (баланс телефона опустился ниже, например, 100 ₽). Поэтому нужен планировщик или триггер, который отслеживает баланс абонента.
2. **Проверка настроек автоплатежа.** Автоплатёж активен, согласие пользователя действует, привязанная карта не просрочена и не заблокирована. Также проверяется, что автоплатёж в этом периоде ещё не выполнялся: идемпотентность нужна, чтобы при повторном срабатывании триггера деньги не списались дважды.
3. **Проверка лимитов автоплатежа.** Сумма разового платежа и общий лимит автоплатежей за месяц не должны превышать заданные пользователем.
4. **Проведение платежа без участия пользователя.** Используется сохранённый токен карты (рекуррентный платёж без ввода CVC и 3-D Secure). Дальше выполняется та же транзакция: BEGIN → проверка и блокировка средств → списание → зачисление и запись в журнал с пометкой «автоплатёж» → COMMIT.
5. **Обработка неудачи.** При нехватке средств или отказе банка выполняется ROLLBACK. Затем запланированы повторные попытки по заданным правилам (например, через несколько часов, не больше N раз). После исчерпания попыток пользователь получает уведомление, а при систематических отказах автоплатёж приостанавливается.
6. **Уведомление и обновление расписания.** Пользователь получает SMS или push-уведомление о списании и зачислении. В настройках автоплатежа фиксируется дата последнего успешного платежа и дата следующего запуска.

## Задание 3. SQL vs NoSQL

### 3.1. Пять преимуществ SQL-систем перед NoSQL

1. **Строгие гарантии ACID и надёжные транзакции.** Реляционные СУБД изначально построены вокруг транзакций, затрагивающих много таблиц и строк сразу. Многие NoSQL-системы жертвуют этим ради скорости и масштабирования и дают только «согласованность в конечном счёте» (eventual consistency) или транзакции в пределах одного документа. Для финансов, учёта и бронирования это критично.
2. **Целостность данных на уровне СУБД.** Схема, типы данных, первичные и внешние ключи, ограничения CHECK, UNIQUE и NOT NULL не позволяют записать некорректные данные, например заказ без клиента или дубликат ИНН. В NoSQL эту проверку обычно приходится писать в коде приложения, и ошибки там случаются чаще.
3. **Единый стандартизированный язык запросов.** SQL — стандарт ISO, который с небольшими различиями работает в PostgreSQL, Oracle, MS SQL Server и MySQL. Знания и запросы переносятся между системами. У NoSQL-систем языки и API свои у каждой (MongoDB Query, CQL, Cypher, команды Redis), и при смене СУБД код приходится переписывать.
4. **Мощные произвольные запросы и аналитика.** JOIN, подзапросы, группировки, оконные функции и CTE позволяют задать новый вопрос к данным без перестройки их структуры. В NoSQL структуру обычно проектируют под заранее известные запросы, а новый отчёт часто требует денормализации, дублирования данных или выгрузки во внешнюю систему.
5. **Зрелость экосистемы.** У реляционных СУБД десятилетия развития: оптимизаторы запросов, проверенные механизмы резервного копирования и восстановления, репликация, разграничение прав, аудит. Вокруг них много BI-инструментов, ORM, ETL-систем и специалистов на рынке, и всё это хорошо документировано.

Ещё одно преимущество — нормализация. Данные хранятся без избыточности, поэтому при изменении (например, адреса клиента) их нужно обновить в одном месте, а не во множестве копий.

### 3.1.* Преимущества NewSQL

NewSQL — это класс распределённых СУБД, которые пытаются объединить сильные стороны обоих подходов: реляционную модель и ACID от SQL плюс горизонтальное масштабирование и отказоустойчивость от NoSQL. Примеры: Google Spanner, CockroachDB, YugabyteDB, TiDB, VoltDB.

**Перед классическими SQL-системами:**

- **Горизонтальное масштабирование «из коробки».** Нагрузку можно увеличивать, добавляя узлы в кластер, а не покупая всё более мощный сервер. Данные автоматически шардируются и перераспределяются, ручное шардирование на уровне приложения не нужно.
- **Высокая доступность и отказоустойчивость.** Данные реплицируются по консенсусным протоколам (Raft, Paxos), поэтому отказ узла или даже целого дата-центра не останавливает работу и не теряет зафиксированные транзакции.
- **Геораспределённость.** Кластер может работать в нескольких регионах сразу, а данные можно хранить ближе к пользователям, что важно и для задержек, и для требований закона о локализации данных.
- **Распределённые транзакции без участия приложения.** ACID соблюдается даже тогда, когда транзакция затрагивает данные на разных узлах.
- **Облачная архитектура** (cloud-native): работа в Kubernetes, обновление версий без остановки, автоматическое восстановление.

**Перед NoSQL-системами:**

- **Строгая согласованность и полноценный ACID** вместо eventual consistency.
- **Привычный SQL**, JOIN, схема и ограничения целостности. Многие NewSQL совместимы по протоколу с PostgreSQL (CockroachDB, YugabyteDB) или MySQL (TiDB), поэтому подходят существующие драйверы, ORM и навыки разработчиков, а миграция проще.
- **Сложные запросы и аналитика**, которые в NoSQL часто невозможны или неэффективны. Некоторые системы (TiDB с TiFlash) совмещают транзакционную и аналитическую нагрузку (HTAP).

**Минусы, о которых стоит помнить:** у NewSQL выше задержки отдельной операции, чем у одиночного сервера, из-за сетевого согласования между узлами. Эти системы сложнее в эксплуатации, моложе классических СУБД и не всегда полностью совместимы с диалектом PostgreSQL или MySQL. Для небольших нагрузок обычная реляционная СУБД часто оказывается проще и дешевле.

## Задание 4. Кластеры

### Критерий выбора типа СУБД: теорема CAP

Для распределённой системы из 1000 машин главный критерий — **теорема CAP (Брюера)**. Распределённая система не может одновременно гарантировать все три свойства:

- **C (Consistency), согласованность:** любой узел в любой момент отдаёт одни и те же, самые свежие данные;
- **A (Availability), доступность:** каждый запрос получает ответ, даже если часть узлов не работает;
- **P (Partition tolerance), устойчивость к разделению:** система продолжает работать, если связь между частями кластера пропала.

На 1000 машинах сбои сети и выход узлов из строя неизбежны и происходят постоянно, поэтому **P обязательно**. Значит, выбирать приходится между двумя классами систем:

- **CP (согласованность + устойчивость к разделению)**: HBase, MongoDB в строгом режиме, NewSQL (CockroachDB, Spanner). Эти системы выбирают, когда ошибка в данных недопустима (финансы, учёт). При сбое часть данных может стать временно недоступной.
- **AP (доступность + устойчивость к разделению)**: Cassandra, Riak, DynamoDB, CouchDB. Эти системы выбирают, когда важно, чтобы система всегда принимала запросы и запись, а небольшое временное расхождение копий допустимо (eventual consistency).

**Для нашей задачи** (массовые вычисления над огромным объёмом данных) обычно подходит **AP или пакетная модель хранения**. Аналитике не нужна мгновенная согласованность каждой записи, зато важны доступность, пропускная способность и масштабируемость. Поэтому подходящие хранилища: распределённая файловая система HDFS (или S3-совместимое объектное хранилище) с колоночными форматами Parquet/ORC, колоночные NoSQL (Cassandra, HBase) или MPP-СУБД (Greenplum, ClickHouse), если вычисления хорошо выражаются через SQL.

Дополнительно стоит учитывать **PACELC**, расширение CAP: даже без сбоев приходится выбирать между задержкой (Latency) и согласованностью (Consistency). Также важны объём и характер данных (структурированные или нет), тип нагрузки (пакетная или потоковая, чтение или запись) и стоимость владения.

### Модель распределённых вычислений: MapReduce

Лучше всего подходит модель **MapReduce**, а на практике — её современное развитие, **Apache Spark** (в экосистеме Hadoop: HDFS + YARN).

Как работает MapReduce:

1. **Map.** Огромный набор данных разбивается на блоки, и каждая из 1000 машин параллельно обрабатывает свою часть, выдавая промежуточные пары «ключ — значение».
2. **Shuffle/Sort.** Промежуточные результаты группируются по ключу и пересылаются на нужные узлы.
3. **Reduce.** Каждый узел агрегирует значения своих ключей, и получается итоговый результат.

Почему эта модель справится лучше всего:

- **Линейная горизонтальная масштабируемость.** Задача делится на тысячи независимых подзадач, поэтому добавление машин почти пропорционально ускоряет вычисления. Архитектура shared-nothing не создаёт общего узкого места.
- **Принцип локальности данных** (data locality). Вычисления отправляются туда, где лежат данные, а не данные гоняются по сети к вычислениям. При петабайтах это главное условие производительности.
- **Отказоустойчивость.** На 1000 машин отказ нескольких узлов во время расчёта — нормальная ситуация. Планировщик автоматически перезапускает упавшие подзадачи на других узлах, а данные хранятся в нескольких репликах (в HDFS по умолчанию 3). Весь расчёт заново начинать не нужно.
- **Простота для разработчика.** Программист пишет только функции map и reduce. Распределение задач, балансировку, повторы и пересылку данных берёт на себя фреймворк.
- **Работа на обычном оборудовании** (commodity hardware). Дорогие специализированные серверы не нужны.

**Почему именно Spark, а не классический Hadoop MapReduce.** Классический MapReduce записывает промежуточные результаты на диск после каждого этапа, что медленно для сложных многошаговых и итеративных расчётов (машинное обучение, графовые алгоритмы). Spark держит промежуточные данные в оперативной памяти (RDD/DataFrame), строит граф вычислений (DAG) и оптимизирует его целиком. На итеративных задачах это быстрее в десятки раз. Модель вычислений та же, а отказоустойчивость обеспечивается пересчётом утерянных частей по «родословной» данных (lineage). Spark также поддерживает SQL (Spark SQL), потоковую обработку и ML-библиотеки.

**Альтернативы в зависимости от задачи:**

- **MPP-СУБД** (Greenplum, ClickHouse, Vertica), если вычисления сводятся к SQL-аналитике над структурированными данными;
- **потоковые модели** (Apache Flink, Kafka Streams), если данные поступают непрерывно и результат нужен в реальном времени;
- **MPI / HPC-подход**, если это тесно связанные научные расчёты с частым обменом между узлами (моделирование, численные методы), а не обработка больших данных.
